02 — The Problem

Solo builders stall — not from lack of ideas,
but from too many open loops.

Every project has a backlog that expands faster than it empties. Feature ideas, bugs, README gaps, missing error handling, half-finished tests — all of it competing for the same limited attention session.

The problem isn't motivation. It's prioritization under cognitive load. When everything feels important, nothing gets done.

Existing tools — Jira, Linear, GitHub Issues — are designed for teams. They surface all your tasks, organized by status and sprint. That's the wrong interface for a solo builder at 11pm who just wants to know: what do I open first?

Easy Wins inverts the model. It reads your project and tells you the one move with the highest impact-to-effort ratio. Everything else is secondary.

The real constraint

Attention is the bottleneck

Solo builders context-switch constantly. A tool that requires upfront configuration or multi-step planning fails the person who has 45 minutes and needs a clear entry point immediately.

Project state is never obvious

After days away from a codebase, the current state — what works, what's broken, what's missing — isn't in anyone's head. It lives in the code. The tool should read the code, not rely on memory.

Progress feels invisible

Fixing bugs and adding docs doesn't feel like forward motion. Without a way to track improvement over time, small wins go unnoticed and motivation erodes even when work is happening.

Generic advice doesn't help

Checklists like "add a README" or "write unit tests" are useless without project context. The tool needs to reason about this project's actual state — not a template.

04 — Design Decisions

Five calls that shaped
how the tool behaves.

01

Today's Win as the primary surface

The report leads with a single hero card: one task, an estimated time, and the exact file to open. Everything else — scores, tracker table, build order — is secondary content behind a "Show full report" toggle.

The decision reflects the core use case: someone sitting down with limited time who needs an entry point, not a dashboard. Full report access is preserved for deeper sessions.

Tradeoff

Power users who want the full report immediately have to click once. Accepted — the default serves the more common case.

02

Local inference over cloud API

The analysis runs against a locally-bundled Gemma 3 1B model via llama.cpp. No API key, no network request, no latency spike when offline. The entire tool works air-gapped.

This was also a deliberate privacy constraint: a developer's codebase shouldn't touch a third-party server unless they choose that. Local-first removes that concern entirely.

Tradeoff

A 1B parameter model produces shallower analysis than a frontier model. The structured output schema compensates — the model fills known slots rather than reasoning freely.

03

Profile detection before analysis

When a folder is selected, the tool runs a lightweight profile detection pass before the full analysis. It reads the project structure and infers likely platform, publishing targets, and readiness focus — pre-filling the analysis profile chips.

This reduces the "configure before you start" friction that kills adoption in productivity tools. Most users can just hit Analyze without touching the profile at all.

Tradeoff

Autodetection adds a second API call and a brief delay. A spinner labeled "Detecting" manages the wait without feeling broken.

04

Saved analyses with delta awards

Analyses are persisted to localStorage, keyed by folder path. On reanalysis, the tool diffs the new report against the previous one and awards points only for actual progress — score gains, issues cleared, stages advanced.

This prevents gaming the system (running the same analysis repeatedly for easy points) and keeps the reward loop honest. Points reflect real work, not activity.

Tradeoff

If the model produces different scores on identical code (due to inference temperature), a reanalysis might not award points even after real work. Acceptable noise in an otherwise subjective scoring system.

05

Confidence transparency

Every report includes a confidence rating (Low / Medium / High) shown next to the project stage badge. When the model is analyzing a sparse or ambiguous project, it says so rather than projecting false certainty.

The principle: a tool that admits uncertainty is more trustworthy than one that doesn't. Users adjust how much weight they put on the results accordingly.

Tradeoff

Displaying confidence means users may dismiss valid findings on sparse projects. Accepted — honest calibration is more useful than inflated confidence long-term.

05 — Stack & Outcomes

Local-first architecture,
structured output, zero dependencies.

Layer Technology Why
Shell Electron Native folder picker, system tray integration, local API token management — things not possible in a pure web app
UI React + TypeScript + Vite Fast iteration with full type safety across the report schema; component-level isolation for each report section
Styles Tailwind CSS v3 + shadcn/ui 40+ pre-built accessible components; consistent dark theme with CSS variable tokens; no custom CSS beyond overrides
Charts Recharts (lazy-loaded) Radar chart for score overview; lazy import prevents blocking the initial render on first load
API Express + axios Local server on port 3001; token-authenticated to prevent other processes from triggering scans; supports both Electron and browser dev mode
Inference Gemma 3 1B via llama.cpp Runs entirely on CPU; no GPU required; bundled with the app so nothing to install; structured JSON output via constrained decoding
Persistence localStorage Zero-config state persistence for saved analyses and achievement history; survives app restarts without a database

What it produces

A single prioritized task

The "Today's Win" hero card extracts the highest-impact, easiest task from the full report and surfaces it immediately — no scrolling, no triage required.

A scored snapshot of project health

Seven completion dimensions scored from 0–100, with a radar chart and a tracker table showing status, priority, and the next concrete action per area.

Platform-specific readiness checklists

If the project targets Steam, the App Store, or WCAG AA, the report includes per-item status and specific remediation steps — not generic advice.

Progress tracking with gamification

Each reanalysis diffs against the previous run and awards points for real improvement. Tiered levels (Started → Gold Standard) convert invisible maintenance work into a legible arc.
